# 业务后台前端 Skills 使用指南

适用于列表、详情、表单、设置、仪表盘等业务后台页面。

核心流程：**Taste 定设计 → React Best Practices 做实现 → Web Design Guidelines 做审查 → 浏览器验收。**

## 1. 三个 Skills 如何分工

| Skill | 职责 | 使用时机 |
| --- | --- | --- |
| `design-taste-frontend` | 确定信息层级、布局、排版和视觉风格，结合截图打磨页面 | 新建页面、整体改版、视觉优化 |
| `vercel-react-best-practices` | 指导 React / Next.js 的组件、数据请求和渲染性能 | 编写或重构 React 代码 |
| `web-design-guidelines` | 对照界面规范审查交互细节、语义和可访问性 | 实现后，以及修改交互后 |

三个 Skills 共用同一套设计规范，不各自重新设计页面。非 React / Next.js 项目跳过 React 专属规则。

Taste 与 Guidelines 的检查侧重不同：前者关注实际视觉效果，后者关注规范落实；两者都不能代替真实业务流程验证。

## 2. 后台开发的统一原则

- 优先保证信息清晰、操作效率、组件一致性和合理的信息密度。
- 沿用现有技术栈、组件库、接口和权限规则。
- 表格、筛选栏、分页、表单、弹窗和抽屉采用统一规范。
- 用颜色表达状态与重点，避免仅靠颜色传达含义。
- 减少装饰性渐变、大面积留白和无意义动画。
- 先把一个代表性页面做完整，再将确定的规范应用到其他页面。
- 不将模拟数据页面视为真实接口集成完成。

## 3. 完整开发流程

### 第一步：了解项目和业务

阅读项目说明、现有页面、路由、公共组件、样式与接口代码，明确：

- 页面供谁使用，最常见的操作是什么。
- 需要展示哪些字段，哪些信息必须优先看到。
- 筛选、分页、编辑和批量操作采用什么规则。
- 已有哪些组件和页面可以复用。
- 哪些权限、接口或业务规则仍不明确。

产出：页面范围、复用方案，以及确实需要补充的信息。

### 第二步：Taste 确定设计

使用 `design-taste-frontend` 的后台 / App Screen 流程，先安排信息和操作，再处理视觉。

统一导航、页面标题、内容区域、表格密度、筛选布局、表单宽度、操作位置、字体、间距和状态颜色。已有成熟规范时直接沿用，不为单个页面重新创造风格。

首次建立规范时，选择一个有代表性的业务列表页，包含筛选、表格、分页和编辑入口。将最终采用的规则写入项目设计文档，供后续页面复用。

产出：页面结构、视觉规范和可复用组件方案。

### 第三步：React Best Practices 实现

React / Next.js 项目使用 `vercel-react-best-practices` 指导实现，结合当前架构采用适用规则。

- 组织组件、状态和数据请求，避免不必要的串行请求、重复请求与重复渲染。
- 复用公共组件，不过度抽象，也不无依据地添加缓存或记忆化。
- 接入真实接口，正确处理查询条件、分页和提交结果。
- 根据页面需要补齐加载、空数据、失败重试、提交中、成功和失败状态。
- 按业务要求处理权限不足、禁用状态与危险操作确认。

产出：可运行、可操作、状态完整的页面。

### 第四步：Web Design Guidelines 审查

调用 `web-design-guidelines`，按其指引读取当前规范，检查新增与修改的 UI 代码。

重点检查表单标签、错误提示、按钮语义、图标按钮名称、键盘操作、焦点可见性、弹窗交互、颜色对比及响应式布局。

记录问题对应的文件位置和原因，修复后复查。不要把代码审查通过等同于实际交互验收通过。

产出：问题修复及仍需处理的明确事项。

### 第五步：浏览器验收

运行页面，结合 Taste 的截图检查流程打磨实际效果，并验证关键操作。

| 验收范围 | 重点 |
| --- | --- |
| 内容边界 | 长文本、较多数据、缺失字段是否导致溢出或错位 |
| 布局 | 常用桌面宽度和窄屏下，导航、表格与操作是否可用 |
| 业务流程 | 筛选、重置、分页、编辑、保存是否正常 |
| 状态反馈 | 加载、空状态、错误和提交反馈是否清楚 |
| 一致性 | 与其他后台页面的间距、组件和状态表达是否一致 |
| 工程检查 | 完成适合本次改动的构建、类型检查及必要测试 |

产出：完成内容、验证结果、尚未验证或受阻的部分。缺少接口、账号或运行环境时如实记录，不声称已经完成验证。

## 4. 按任务选择流程

| 场景 | 使用方式 |
| --- | --- |
| 新建后台、整体改版 | 完整流程，先确定代表性页面与公共规范，再扩展 |
| 新增列表页、详情页 | Taste 沿用规范 → React 实现 → Guidelines 审查 → 浏览器验收 |
| 修复交互或接口问题 | React 实现为主，Guidelines 检查受影响部分，验证相关操作 |
| 美化现有页面 | Taste 为主，Guidelines 审查，涉及 React 逻辑时再应用 React 规则 |
| 调整文案、间距等小改动 | 按已有规范修改，做针对性检查，无需完整重跑全部流程 |

## 5. 可直接复制的开发提示词

在下面的提示词之前补充具体任务，例如“完成商品管理页，支持关键词筛选、状态筛选、分页和编辑”。

```text
请使用以下三个 Skills 完成本次前端开发：
- design-taste-frontend
- vercel-react-best-practices
- web-design-guidelines

这是高频使用的业务管理后台。目标是信息清晰、操作高效、
视觉统一和维护方便。

1. 先了解项目
阅读项目说明、现有页面、路由、组件库、样式规范和接口。
识别可复用的组件与布局，沿用现有技术栈和业务流程。
如果不是 React / Next.js 项目，跳过 React 专属规则。

2. 使用 design-taste-frontend 确定设计
按后台 / App Screen 场景执行。
先确定信息层级与主要操作，再设计视觉样式。
统一导航、标题、表格、筛选、分页、表单、抽屉和弹窗。
优先保证信息密度和数据可读性，复用现有组件库。
减少装饰性渐变、大面积留白和无意义动画。
已有规范时沿用，首次形成的公共规范写入项目文档。

3. 使用 vercel-react-best-practices 实现
连接真实接口，合理组织组件、状态和数据请求。
避免不必要的串行请求、重复请求和重复渲染。
不做缺乏依据的性能优化。
补齐相关加载、空数据、错误、重试、提交和权限状态。
遵循现有接口和权限规则，不把模拟数据当成接口集成完成。

4. 使用 web-design-guidelines 审查
按 Skill 指引读取当前规范，审查新增和修改的 UI 代码。
重点检查表单标签、错误提示、按钮语义、图标按钮名称、
键盘操作、焦点、弹窗交互、颜色对比和响应式布局。
发现问题后直接修复，并复查修改结果。

5. 浏览器验收
运行页面，使用 Taste 的视觉检查流程检查截图并打磨。
验证长文本、较多数据、窄屏、筛选、分页、编辑和保存。
确认加载、空状态、错误状态及页面间的一致性。
完成适合本次改动的构建、类型检查和必要测试。

最终说明完成内容、验证结果，以及尚未验证或受阻的部分。
根据本次任务大小缩减流程，不为局部修复重做整个设计。
```
